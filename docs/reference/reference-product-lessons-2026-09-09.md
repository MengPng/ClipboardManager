# 参照产品更新说明的经验提取与差距清单（2026-09-09）

## 目的与使用方式

本文档提取一款成熟 Windows 剪切板工具（Quicker 平台上的第三方剪切板动作）四年半公开更新说明中的工程教训，并逐条对照本项目当前实现，形成差距清单。

用途限定为**风险预警与优先级参考**：

- 它记录的是别人已经踩过的坑，用于避免我们重复设计错误，尤其是 WPF 窗口状态、剪切板格式互操作和数据可靠性三类。
- 它**不是**需求清单。参照产品运行在 Quicker 宿主内，有大量与本项目无关的能力（动作管理、超级菜单、捷径面板、文件菜单、图标管理器）。本文只保留与本项目范围相关的部分。
- 引用的版本号与日期用于回溯原始条目，不代表我们要实现同名功能。

## 一、数据可靠性：该产品代价最大的一类事故

按事故密度和用户可见损失排序，收藏数据丢失排第一，远超剪切板捕获本身的问题。

| 证据 | 条目 |
|---|---|
| `v0.4.6` | 收藏条目重启电脑后全部消失，重新加入后一点就报错 |
| `v0.8.4` | 收藏内容修改 Title、Icon 后自动保存，策略为改动后 0.5 秒 |
| `v0.8.1` | 收藏夹内容修改 Title 后自动保存 |
| `2022.11.22` | 修复收藏夹中拖拽时数据没有保存的问题；修复一系列数据没有保存的问题 |
| `2022.11.20` | 使用数据库进行存储，提高存储性能以及数据的稳定性 |
| `v0.3.2` | 数据导入改为同步调用 |
| `v0.8.25` | 数据导入失败导致无法使用 |
| `2022.11.29` | 修复数据导入失败的问题 |
| 专题页 | 「收藏数据好像不在了？」单独成页 |

可提取的结论：

1. **收藏项的每次编辑必须是即时事务提交**，不能依赖窗口关闭、失焦或进程退出时统一落盘。`v0.8.4` 和 `v0.8.1` 连续两个版本补「修改后自动保存」，说明此前存在「用户改了、看起来生效了、重启后丢失」的窗口期。参照产品最终采用 0.5 秒防抖后写入。
2. **软删除必须配一个用户可见的还原入口**。参照产品在 `2022.11.20` 引入回收站，`2022.11.22` 才补齐还原功能。本项目已有 `deleted_at` 软删除，但界面上删除即不可回退，用户侧等价于硬删除。
3. **导入路径是一条独立的高危路径**。三个不同版本都在修「导入失败」，且 `v0.8.25` 的后果是「导致无法使用」——即导入失败会污染主数据并阻塞启动。任何导入功能都必须先备份、失败可回滚，不得就地改写主库。
4. **清理的触发时机会影响退出体验**。`v0.1.21` 从「退出时清理」改为「每 10 分钟清理」以避免退出卡顿，`v0.1.22` 又改为「失去焦点后清理」并注明「定时清理不太合适」，`v0.1.28` 把清理移入后台线程防止卡 UI。结论是清理既不能挂在退出路径上，也不宜用固定定时器，应由空闲或失焦事件驱动且始终在后台线程执行。

## 二、窗口可见性是一个状态机，不是若干独立开关

参照产品在这一处至少修了七次，且每次修完都会因为新的组合再次出问题。

| 证据 | 条目 |
|---|---|
| `v0.2.1` | 贴边时，粘贴会导致面板意外隐藏 |
| `v0.4.4` | 开启折叠隐藏时，点击固定后会自动折叠窗口 |
| `v0.4.5` | 禁止贴边后剪贴板只能手动关闭；非固定情况下粘贴后没有自动隐藏 |
| `v0.4.13` | 贴边时粘贴会导致面板关闭；记忆贴边隐藏设置项（重启后失效） |
| `v0.5.0` | 贴边时粘贴不隐藏，鼠标离开后再隐藏 |
| `v0.6.2` | 自动运行时按条件恢复打开状态，做法是延迟 1 秒存储 `IsVisible`，重启后恢复 |
| `v0.8.33` | 非固定状态下弹出窗口导致界面隐藏 |
| `2022.4.12` | 修复启动时窗口没有自动隐藏 |
| `2023.4.15` / `2023.4.28` | 窗口可折叠；增加用折叠代替隐藏的选项 |

这些不是七个独立缺陷，而是 `固定(pin) × 贴边停靠 × 折叠 × 失焦隐藏 × 粘贴后隐藏 × 子窗口弹出` 这一组维度未被显式建模的后果。

**结论：如果本项目要引入停靠或固定，必须先把可见性写成显式状态机并覆盖组合用例，否则会逐个复现上述缺陷。**目前本项目只有失焦隐藏一条规则，尚未进入该风险区，但这也是当前与参照产品体验差距最大的地方。

### 一个必须避免的判定错误

`v0.8.53` 记录了一次难以定位的故障：宿主的编辑器复制内容后出现失焦，剪切板窗口「看起来也获取到了焦点（但是没有显示）」，于是呼出时 toggle 判定为 hide，窗口再也无法呼出。原文注明「具体原因不太清楚，目前只能暂时用这种方法解决问题」。

**结论：显示/隐藏的 toggle 判定不得依赖「本窗口是否持有焦点」或任何可被外部抢占的系统状态，必须依赖自身维护的可见性字段。**

## 三、置顶项：一个反复引发缺陷的设计源头

这是对本项目最直接可操作的一条。

| 证据 | 条目 |
|---|---|
| `v0.3.0` | 置顶项超过 10 个时，「防止重复复制」的选项失效 |
| `v0.7.5` | 单点任何一个条目都会自动跳转到置顶的那个条目 |
| `v0.7.6` | 粘贴后置顶，没有效果 |
| `v0.7.8` | 粘贴后置顶移入筛选策略，设置界面原选项删除 |
| `2022.4.12` | 增加 `paste_current` 命令，可忽略置顶条目 |
| `2022.11.20` | 修复清空时，置顶的条目也被清空的问题 |

同一个置顶标志同时参与**排序**、**去重扫描窗口**、**键盘导航索引**和**清理范围**，四年里在这四个维度上各出过一次问题。`v0.3.0` 尤其值得注意：去重逻辑使用了「取前 N 条」这类窗口，置顶项一旦超过窗口容量就会把待比较的普通项挤出去，导致去重静默失效。

### 对照本项目

本项目目前同样使用 `is_pinned` 让置顶项排在同一列表前部。2026-09-09 已核对代码，结论如下：

1. **已复现同类缺陷（需修复）**：`ClipboardPayloadCaptureService.CaptureAsync` 的图片与文件去重先用 `SearchAsync(new ClipboardQuery(workspace.Id, ItemType: ..., Limit: 500))` 取回至多 500 条，再在内存中 `FirstOrDefault(x => x.ContentHash == ...)` 比对。而 `SqliteClipboardHistoryRepository.SearchAsync` 的排序是 `ORDER BY is_pinned DESC, captured_at DESC`，置顶项占据窗口头部，图片或文件超过 500 条后窗口外的重复项会漏检并新增记录。成因与参照产品 `v0.3.0` 一致，只是窗口从 10 变成 500。文本路径无此问题：`CaptureTextAsync` 在事务内按 `workspace_id + item_type + content_hash` 精确查询，且 `ix_clipboard_items_content_hash` 索引已存在，只是图片与文件路径没有使用它。
2. **同一处还缺事务**：图片与文件是「先查后写」且两步不在同一事务内，快速重复捕获存在插入两条同哈希记录的竞态。修复方向是为图片与文件提供与 `CaptureTextAsync` 等价的事务化合并方法，复用既有哈希索引。
3. 键盘上下导航的索引应基于视图实际渲染顺序，避免「置顶项与普通项混排」时选中项跳变。
4. **清理范围已正确，无需改动**：`ApplyRetentionAsync` 的过期清理与超量清理两条语句均带 `is_favorite = 0 AND is_pinned = 0`，收藏与置顶都受保护，未复现参照产品 `2022.11.20` 的缺陷。

## 四、剪切板格式互操作：格式优先级不能是固定链

这是教训密度最高的一类，且全部来自真实应用的行为差异。

| 证据 | 条目 |
|---|---|
| `v0.2.0` | 修复新版本微信中，复制图片变成了文件的问题 |
| `2022.11.27` | 修复网页上复制图片被处理为纯文本的问题 |
| `2022.12.16` | 再次修复网页中复制图片，无法显示的问题 |
| `2022.11.30` | 修复 Excel 中复制，多显示了一个图片的问题；修复浏览器复制的图片被意外清理的问题；catch 剪贴板数据无效的报错 |
| `2022.11.28` | 修复微信只能复制一次的问题 |
| `2022.11.25` | 对 QQ 中复制的内容，图文混排处理 |
| `2022.12.16` | 修复 QQ 富文本显示出错的问题；优化微信粘贴大图片的速度 |
| `2022.12.18` | 针对 QQ、微信，图文多选粘贴的优化 |
| `v0.2.2` | Html 格式无法正常粘贴 |
| `v0.7.0` | 优化贴图功能，支持批量贴图；修改前会直接合并内容贴图，导致贴出来的是文件 |
| `v0.7.1` | 文件无法贴图 |
| `v0.3.0` / `v0.1.52` | 支持并修复 PixPin、Snipaste 贴图 |

**结论：当剪切板上同时存在 `Bitmap`、`FileDrop`、`HTML`、`UnicodeText` 时，选用哪个格式无法用一条固定优先级链解决，需要结合来源进程做启发式判断。**微信会把图片放成 `FileDrop`，浏览器会把图片同时放成 `HTML` 与 `UnicodeText`，Excel 会额外附带一份图片表示。

### 对照本项目

本项目 `ClipboardPayloadCaptureService` 目前采用单一固定优先级。这意味着在微信复制图片时会记为文件列表，在浏览器复制图片时可能记为纯文本。建议：

1. 引入「来源进程 + 可用格式集合」的格式选择策略，并为微信、QQ、主流浏览器、Excel 建立特例，特例表可配置。
2. 读取任何格式的载荷都必须包裹异常处理。`2022.11.30` 的「catch 剪贴板数据无效的报错」和 `v0.1.10` 的「获取剪贴板内容时添加一个 try catch」是同一条教训，`AGENTS.md` 的有限重试要求已覆盖竞争但未覆盖「格式声明存在、实际数据无效」这一情形。
3. HTML 与富文本格式当前不在本项目范围内。若后续加入，需注意它是独立的一类缺陷源（`v0.2.2`、`2022.12.16`）。

## 六、排序稳定性

| 证据 | 条目 |
|---|---|
| `v0.8.31` | 批量添加后顺序错乱，以及粘贴后排序不稳定 |
| `v0.1.8` | 添加了一个二次排序参数 `SubIndex`，用于对拆分过后的条目进行排序（这样可以全部设置为一样的时间） |
| `2022.4.30` | 优化排序算法，减少卡顿 |
| `v0.8.60` | 按使用次数的筛选，重启过后重置为全部（这个筛选会导致剪贴板不显示新收集的内容） |

两条结论：

1. **排序必须有稳定 tiebreaker。**批量插入时时间戳会落在同一毫秒，仅按时间排序必然乱序。参照产品的解法是显式的二次排序字段。本项目在批量收藏、按行拆分等场景下会遇到同样问题。
2. **持久化的筛选条件会让用户误判程序故障。**`v0.8.60` 的处理是让该筛选在重启后重置为全部。更稳妥的做法是在结果为空时明确提示「当前筛选条件隐藏了 N 条记录」，而不是静默显示空列表。

- 「虚拟化」不能只依赖 `VirtualizingStackPanel`。图片网格布局需要自定义 `VirtualizingWrapPanel`，这是一个明确的实现成本。

- 计划中的「悬浮显示置顶、收藏按钮」会同时命中上表的最后两条陷阱。

| `v0.5.0` | 多选粘贴可弹出多个菜单：按选择顺序粘贴、正序粘贴、逆序粘贴 |
| `2022.4.1` | 搜索框支持 `PageUp`、`PageDown` 翻页 |
| `2022.4.1` | 右键增加「复制」，只会写入剪贴板，但是不粘贴 |

对照本项目：

1. **`Esc` 缺少「先取消多选」这一级。**本项目 `README.md` 定义为「清空搜索或关闭面板」。虽然目前没有多选功能，但选择状态的生命周期规则应提前确定：选择状态随面板隐藏而清空。
2. **危险操作不应有裸快捷键。**`v0.1.34` 直接禁用了清空的键盘触发。这比 `AGENTS.md` 中「输入框编辑不得触发记录删除」更进一步——清空这类不可逆操作即使在列表焦点下也不该只靠一个按键触发。
3. 本项目的 `Enter` 写回与 `Ctrl+Enter` 写回并粘贴，已等价于参照产品「复制」与「粘贴」的分离。

## 九、多显示器与窗口定位

| 证据 | 条目 |
|---|---|
| `2023.3.4` | 修复显示器变化导致剪贴板窗口没有出现在当前屏幕中的问题；重启后判断位置，强行矫正到屏幕中 |
| `v0.1.18` | 自动保存自定义窗口的位置（使用窗口标识），下一次启动时恢复；启动位置判断策略选项 NA |
| `v0.1.35` | 保存窗口大小，并使用上次窗口大小 |
| `2022.4.25` | 可设置自动运行时显示窗口的位置 |
| `2022.4.21-22` | 增加使用键盘方式触发时，是否移动到鼠标周围的选项 |
| `2022.4.2` | 贴边距离优化 |

**结论：「恢复上次窗口位置」与「矫正到当前可见屏幕工作区」必须成对实现。**只做前者，用户拔掉外接显示器后窗口会落在可见区域外，症状表现为「程序打不开」——与本项目 `README.md` 中 `0.4.5` 修复的「双击 EXE 无任何反应」是同一类用户感知。

本项目 Phase 4B 已实现「当前显示器工作区定位」，但尚未验证多显示器与非 96 DPI 环境（见 `docs/acceptance/phase4-desktop-2026-09-09.md`）。参照产品在这一项上确实出过线上问题，该待验收项不应被降级。

## 十、关于偶发故障的方法论印证

`2022.4.15` 与 `2022.4.16` 连续两天都写着「尝试修复某些电脑无法打开设置界面的问题!!!!!」，`v0.8.53` 也注明「具体原因不太清楚，目前只能暂时用这种方法解决问题」。

这与本项目 `0.4.5` 的处境完全一致——`README.md` 已如实记录「原始卡死为偶发现象，本次未能复现，因此无法证明共享缓存就是其根因」。参照产品的经历从反面印证了本项目接入 Serilog 文件日志、并做到「启动的每一步在执行前先记录、日志最后一行即为卡住的步骤」是正确且必要的投入。环境差异型故障无法靠本机复现修复，只能靠日志兜底。

参照产品的相关动作还包括：`2023.4.26` 输出 log 到宿主日志、`v0.1.29` 检查宿主版本过低时禁止运行、`v0.1.15` 与 `2022.4.20` 重写版本管理策略并保证向上兼容。

## 十二、本项目已优于参照产品的部分

记录在此以避免误判为差距：

- **Workspace 数据归属与隔离**：参照产品无此概念，本项目从数据模型起就带 `workspace_id` 与 `device_id`。
- **自身写回防循环**：本项目使用预期哈希一次性标记；参照产品的更新说明中未见等价机制，`v0.4.3` 的「多选复制的内容不收集到记录中」是同类问题的局部处理。
- **Win32 交互契约的严格程度**：`AGENTS.md` 对 `INPUT` 原生布局、`SendInput` 完整事件数、`OpenClipboard` owner 句柄和 UIPI 限制的要求，比参照产品的反复试错更明确。
- **备份与验证后恢复**：本项目 Phase 4F 已具备一致性备份、归档与 schema 验证、失败回滚和离线恢复命令。参照产品仅有导入导出。
- **可复现发布与升级验收**：本项目有 MSI 升级、SHA-256 一致性核对和用户数据保持证据。
